# Agent Note: 固定仓库快照上的只读健康检查

Status: implemented

## Problem

PR Review 只覆盖变更，维护者还需要了解默认分支及已有 CI 数据的当前状态。现有 Job、发布和 finding 身份依赖 PR，直接复用会产生虚构 PR 或把历史报告误当作最新结果。定时触发和失败重试还可能重复消费模型预算。

## Decision

现有 PostgreSQL 队列使用独立 HEALTH_AUDIT Job，固定默认分支 SHA、30 天窗口及仓库配置。HealthReport 按 Job 唯一保存，并与 Job 终态在同一事务提交；重复保存保留首次报告和对应状态，不进入 GitHub publication 或 Reply 状态机。

保留单 Worker；领取时优先处理 PR、Reply 和 Decision。定时只支持关闭、每日、每周，默认关闭。仓库行锁与活动任务唯一约束合并手动／定时重复请求；漏周期最多触发一个当前检查。

验签后的 installation 删除／暂停和仓库移除事件只停用该 installation 内的已登记仓库。事件不负责注册新仓库；已取消或被替代的任务不能被迟到的完成／失败回写重新激活。

Health Auditor 使用现有 Pi 会话执行器和服务自有只读工具。服务生成有文件／字节上限的清单，记录实际读取范围、Memory 版本和 CI 来源。所有采集与模型操作共用取消和总时限。模型结果不决定身份、覆盖范围、来源链接或外部写操作。

每次 Provider 请求前先持久化本次最大预留，收到 usage 后结算；重试与异常恢复从已持久化的实际／未知消耗中扣除额度。进程消失时，尚未结算的请求保守保留为未知消耗。

报告保存在管理页。趋势只比较相同范围、采样／检查／模型／Memory 版本及数据完整度下的指标，不自动认定问题修复。CI 无权限、无匹配 SHA、窗口外和截断均显式保留。

## Alternatives considered

- 复用 PR 字段与 Review publication 能少改现有入口，但健康任务没有真实 PR，也不向 GitHub 发布；明确的 Job 类型和独立报告保留资源归属与副作用边界。
- cron 平台、Redis 和第二个 Worker 有利于复杂排期与吞吐，但当前只有固定日／周周期和少量仓库，已有数据库与进程内触发器足够。
- 每次重试重新分配预算实现简单，却让同一任务的费用随重试放大；因此先持久记账再发送请求，累计实际与未知消耗。
- 执行仓库测试／扫描可以产生最新结果，但需要新的不可信代码执行隔离；当前只读源码与已存在的 GitHub 证据，并明确缺失。
- 综合健康分与自动“已修复”便于浏览，却会把模型和覆盖变化误读为代码改善；当前只展示可比指标与证据。

## Consequences

健康检查复用现有服务、队列、授权和 Session，报告能够追溯到固定 SHA 与实际读取证据；手动、定时、重试和异常恢复共享明确的任务身份与费用边界。

每轮请求前增加一次数据库写入，对数据库可用性有依赖。单 Worker 不抢占已运行的健康任务，因此 PR 可能等待一个有界的健康任务结束。字节估算和未知消耗较保守，可能提前耗尽额度。读取不到 CI 或未完整覆盖文件时报告为 partial，不代表全仓库安全保证。

文件上限经常阻止目标仓库覆盖时，再考虑固定快照内的分批检查；吞吐实际影响 PR 协作后，再评估调度抢占或 Worker 扩展。

## Verification

Node / PostgreSQL 回归覆盖任务去重、报告原子性、请求前预留、重试预算、取消、权限、文件／行号／来源校验和趋势。实际命令、固定 SHA、两次真实模型记录与界面证据集中在 [M3 清单](../../../../docs/tasks/M3.md)。
