# Agent Note: 管理页的临时状态、授权复用与讨论分页

Status: implemented

## Problem

OAuth 登录放弃后，过期 state 和不再访问的 session 留在内存。管理页首次加载对同一批仓库重复授权，讨论 API 又一次返回全部历史回复。请求和历史数据增加时，这些行为扩大内存、远端调用和响应成本。

## Decision

[管理 API](../../../../src/admin.ts) 使用有界 ExpiringStore：state 保留 10 分钟，session 保留 8 小时，各最多 1000 条。每条记录的 unref 定时器在到期后删除引用；读取也检查截止时间。容量满时拒绝新登录并返回 503，不踢出有效会话。有效 callback 消耗一次 state；退出清理对应 session 及定时器。

`GET /api/bootstrap` 一次获取可访问仓库，再读取这些仓库的 Job 与 Memory。一次请求最多并发 4 项 GitHub 权限检查；下一次请求重新授权，不跨请求缓存权限。原独立端点保留，写操作继续执行独立授权和 CSRF 校验。

`GET /api/findings` 返回 `{ items, nextCursor }`。默认每页 50 条，limit 为 1～50，支持 repositoryId 和 jobId。排序键为讨论创建时间、finding ID、回复 comment ID，全部降序；时间游标保留 PostgreSQL 微秒，comment ID 保留十进制字符串。游标包含筛选条件并使用服务会话密钥签名，每页仍重新授权。无权仓库返回空列表；无效、被修改或筛选不一致的游标返回 422。

[管理界面](../../../../admin/app.tsx) 按用户操作加载下一页，显示已加载数量，提供重试、刷新及仓库筛选；切换筛选或离开页面时取消旧请求。审查详情用单独的 `finding_statuses` 显示当前状态，不依赖讨论是否已经翻到对应页。没有完整报告的历史审查只声明已加载的问题数量。

## Alternatives considered

- Redis 或持久 session：当前单进程服务无需增加外部存储；进程重启后重新登录的既有行为保持不变。
- 只在请求时清理：空闲时仍保留过期 OAuth token；定时到期删除同时覆盖无人回访的记录。
- 满额时淘汰最早的有效会话：可缓解新登录等待，但会使已有维护者被迫退出，因此使用明确的容量错误。
- 长期权限缓存：可继续减少调用，但延迟权限撤销；聚合端点已消除首次加载的三重查询，并保留下一请求的实时授权。
- OFFSET 分页：实现简单，但头部新增记录可能导致后页重复；使用稳定复合游标，同时避免时间降为毫秒造成遗漏。
- 自动拉取全部讨论：仍会把历史数据成本集中到一次页面访问，因此下一页由用户主动加载。

## Consequences

首次加载的权限检查从约 3N 次降为 N 次；每页最多返回 50 条讨论。API 调用方需要适配新的分页 envelope，管理页随服务一起构建部署。新增数据不会主动插入正在浏览的历史列表，刷新后重新获取。

游标不是数据库快照：同时新增回复或删除记录时，列表不承诺跨请求冻结；对未改变的行保证稳定顺序，不声称压力测试或线上容量验证通过。逐页响应有界，但用户持续点击加载更多仍会增加浏览器中保留的记录。存储容量和 TTL 是服务常量，满额可能要求稍后重试；没有引入自动扩容。
