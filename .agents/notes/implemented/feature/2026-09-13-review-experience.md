# Agent Note: 用问题和团队规则组织用户体验

Status: implemented

## Problem

完整流程把审计结构铺在 PR 和规则首页；同一根因的多个位置生成多个评论，用户难以快速判断要做什么。只在正文提到规则还会失去结构化关联。规则列表按最新版本筛选时，也会把仍然有效的旧版本藏起来。

## Decision

展示文本只生成一次：单 Agent 同时给出完整候选、分组和短评；专项只提交完整候选，由 Main 统一聚合与生成短评。服务检查成员完整性、120 字符上限、位置与规则引用，保存关联位置、各候选的角色、严重度和完整依据。模型不能自行生成身份、合并数量或关联位置。

PR 默认展示数量、短标题和“问题 → 原因 → 建议”；来源和完整依据进入二级入口。摘要位置也有可展开的简短修改建议。服务只使用评论末尾的身份标记绑定线程，代码示例中的类似文本不能改变绑定。

管理页主导航为概览、团队规则和仓库。原生 dialog 提供右侧详情与停用确认，复杂编辑使用独立 hash 页面；来源、历史与技术信息逐级展开。运行记录、策略、讨论与健康检查进入设置；健康首页只展示实际意见和覆盖缺口。

待确认更新不撤销旧版；忽略更新后列表恢复展示生效版本，版本号继续递增。替代操作同时结束替代规则自身的旧生效版本，并与普通确认共用例外校验，保留原有来源和作用域。

## Alternatives considered

- 只截断原报告会丢失修改要求，也不能解决重复根因；使用独立的有界展示字段。
- 再增加聚合 Agent 会增加请求与等待；复用单 Agent 和 Main 的既有输出。
- 要求每个专项重复生成短评会引入没有展示价值的格式失败；专项保持完整候选输出。
- 删除审计和生命周期数据会破坏追溯；保留数据，改变默认展示层级。
- 引入 UI 库、路由平台或新状态机成本过高；使用现有 React、hash 链接和原生 dialog。

## Consequences

语义分组仍依赖模型；服务证明成员与引用的一致性，不能证明两个问题语义相同。模型结构失败继续按既有规则拒绝或形成 partial，不能伪装全覆盖。旧报告兼容显示，不凭空重写历史。

没有增加手工造无来源规则、使用统计、健康总分或新的外部写操作。真实模型对照与浏览器验证的输入、结果、消耗和限制见 [UX 清单](../../../../docs/tasks/UX.md)。

## Verification

使用现有 Node、数据库和浏览器验证入口；可重复的固定样本入口为 scripts/evaluate-ux.mjs。所有实际命令和证据集中在 UX 清单，M2 的独立人工增益验收继续保留。
