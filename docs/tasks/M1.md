# M1：Decision Extraction → Team Memory → Future PR Review

状态：已完成｜前置阶段：M0 已完成｜更新：2026-09-11｜完成：9 / 9

M1 在 M0 已验证的 GitHub App、Webhook、固定提交 Workspace 和单 Agent Review 主链上，补齐以下产品闭环：

```text
PR A merged
→ Decision Extractor
→ CANDIDATE Memory
→ Maintainer 确认
→ ACTIVE Memory
→ PR B Review 召回并引用
```

需求来源：

- [PRD-MVP](../PRD-MVP.md)

## M1-01｜PostgreSQL 与持久任务基础

### 已实现

- 使用 `pg` 和顺序 SQL migration，不引入 ORM 或第二套 migration 工具。
- 持久保存 repository、Webhook delivery、Job、发布结果、Memory 版本和审计记录。
- Webhook 在同一事务中保存 delivery 与 Job，提交后才返回 `202`；数据库失败返回 `503`。
- `delivery_id` 和自动 Job 业务键均有唯一约束。
- 支持 `PR_REVIEW` 和 `DECISION_EXTRACT` 两种 Job。

### 完成证据

2026-09-11，本地 PostgreSQL 18.6、`pg@8.23.0`。migration 命令为 `npm run migrate`。

`npm run test:db` 验证：空库 migration、重复 migration、重复 delivery、数据库不可用、跨连接读取 queued Job。真实 GitHub delivery `ada59950-ad86-11f1-87ad-38c740300859` 重投后，数据库仍为 1 条 delivery 和 1 个 Job。

## M1-02｜持久 Job 执行、恢复、重试与发布幂等

### 已实现

- PostgreSQL 单 Worker 使用 `FOR UPDATE SKIP LOCKED` 领取任务。
- 状态支持 queued、running、succeeded、partial、failed、timeout、superseded、cancelled、uncertain。
- 启动时恢复异常遗留的 running Job。
- 暂时错误最多执行 3 次，指数退避并尊重 GitHub `Retry-After`；永久权限与输入错误不循环重试。
- 新 head 淘汰尚未运行的旧 Job；发布前重新检查仓库、PR、Draft、head 和 repository enabled。
- Review fingerprint、GitHub Review ID/URL 和 uncertain 状态持久化，不宣称 exactly-once。

### 完成证据

`npm run test:db` 验证 running 恢复、暂时错误 3 次、403 永久错误 1 次、发布结果持久化。`npm test` 验证新 head、固定 `commit_id`、uncertain 不盲目重投和 `Retry-After=17` 保留。

真实恢复样本使用 PR #5 的 Job `eaf7789c-7053-4607-b390-4e5f5b4d4612`：运行中终止 Worker，重启日志为 `jobs_recovered count=1`，恢复后 attempt=2 并成功。成功收尾会清空旧 `last_error`，migration `002_clear_succeeded_job_errors.sql` 修正已有数据。

## M1-04｜Decision Extractor 与候选决策

### 已实现

- 每个 merged PR 建立独立 Pi `AgentSession`，由确定性路由触发。
- 只接受 architecture decision、engineering rule、security rule、coding convention、exception 和 deprecated pattern。
- Proposal 必须包含 Scope、来源 PR/merge SHA/comment IDs、人类评论与当前 PR 代码双证据、confidence 和 uncertainties。
- AI 评论、仅代码写法、争议和无来源建议不能成为 Candidate；无决定允许返回 `[]`。
- 模型只能创建 CANDIDATE，不能激活规则。

### 完成证据

`test/decision.test.ts` 的 5 项测试覆盖明确规则、空结果、结构字段诊断、无效人类证据、争议、例外、替代关系和稳定指纹。

真实 PR #2 首次暴露 Prompt 只列字段名、未定义嵌套契约的问题；服务端拒绝了不完整输出。补充精确 JSON 契约后，同一 snapshot 重跑成功，由 `deepseek-v4-flash` 生成 1 条 Candidate。PR #1 与 PR #5 没有可复用人类决定，真实输出均为 0 Candidate。

## M1-05｜Team Memory 数据模型与生命周期

### 已实现

Memory 保存稳定 ID、version、repository/installation ownership、type、title、content、rationale、Scope、source、evidence、confidence、uncertainties、状态、例外/替代关系、确认者和时间。

状态流转为：

```text
CANDIDATE → ACTIVE
CANDIDATE → REJECTED
ACTIVE → SUPERSEDED
ACTIVE → DEPRECATED
```

修改 ACTIVE 会创建新 CANDIDATE version，不覆盖旧版本。所有 mutation 在事务中记录真实 actor、前后值和时间；同一来源使用稳定指纹去重。

### 完成证据

`npm run test:db` 验证 Candidate、ACTIVE、REJECTED、SUPERSEDED、DEPRECATED、版本、Scope、仓库隔离、重复来源和 audit。

真实 Memory `df080917-5a9d-4059-9b3c-e0be1fdd0dd8`：

- v1 于 2026-09-10T15:21:08.906Z 由 GitHub user `M2tHane`（ID `83757644`）激活。
- 编辑产生 v2 CANDIDATE；v2 于 2026-09-10T15:28:18.283Z 激活。
- v1 同一事务转为 SUPERSEDED；v2 保持 ACTIVE。
- 最终 Scope：`backend/**/dto/**/*.java`。

## M1-06｜Memory 检索接入 PR Review

### 已实现

检索固定按 authorization、repository、ACTIVE、Scope、文本相关性、Top-K 顺序执行。M1 使用 Node `matchesGlob` 和轻量文本排序，不引入 pgvector。

传入 Agent 的 Memory 包含 ID、version、title、content、rationale、Scope 和 source。服务端发布前再次验证模型引用的 ID/version 确实位于本次召回集、仍为 ACTIVE 且属于当前仓库；source 由服务端真实记录回填。

无法可靠映射行内位置时发布 COMMENT Review summary，不猜 GitHub 行号。

### 完成证据

- 相关路径：[PR #3 Review v1](https://github.com/M2tHane/pi-review-test-repository/pull/3#pullrequestreview-5169008888) 引用 Memory v1、来源 PR #2 与 comment `5620921376`。

## M1-07｜Maintainer 身份认证与管理 API

### 已实现

- GitHub App OAuth Web Application Flow：随机 state、callback 校验、code 换 user token、读取当前用户。
- user token 仅保存在服务端内存 Session，不写业务表、不发给浏览器。
- Session Cookie 为 HttpOnly、SameSite=Lax，HTTPS callback 下带 Secure；mutation 同时校验 Origin 与 CSRF token。
- 每个敏感操作按 Memory 实际 ownership 重新查询 repository，并实时要求 GitHub `maintain` 或 `admin` 权限。
- API 支持 repositories、jobs、memories 的 list/get，以及 repository 配置和 Memory approve/edit/reject/supersede/deprecate。
- repository pause 阻止新 Job和待发布 Review；include/exclude paths、输出语言和 token budget 接入审查执行。

### 完成证据

GitHub App callback 配置为临时 HTTPS tunnel 的 `/auth/github/callback`，`Request user authorization during installation` 保持关闭。真实 OAuth 登录识别 user `M2tHane`，并成功授权操作测试仓库 Memory；client secret、user token 和 Session secret 均未进入前端、提交或普通日志。

`npm run test:db` 验证错误 state=400、未登录=401、错误 CSRF=403、授权 approve=200、跨仓库 mutation=403，以及暂停仓库不创建新 Job。

### 最终验收

以下闭环同时成立：

```text
M0 GitHub → Pi → COMMENT Review
+
merged PR → 可追溯 CANDIDATE
+
Maintainer OAuth 确认 → ACTIVE
+
相关 PR 正确召回并引用
+
Scope 外 PR 不误用
+
SUPERSEDED 版本不再召回
+
running Job 跨重启恢复
+
mutation 服务端鉴权
```

## 数据与边界

- Pi Session 是单 Job 执行上下文，Job 结束即释放；Team Memory 是 PostgreSQL 长期知识。
- GitHub 一级事件、验签、权限、幂等、Scope 和发布判断均由服务代码处理。
- Agent 只获得绑定当前 Workspace 的只读工具，不加载待审仓库中的可执行扩展。
- 只有 ACTIVE Memory 可以作为团队现行规则；模型不能激活规则或改写资源归属。
- GitHub Publisher 只发布 COMMENT，不自动 APPROVE、REQUEST_CHANGES、修改源码、push 或 merge。
- 密钥、installation token、OAuth token、模型 Key 和私有 payload 不进入提交或普通日志。
